# 제한시간 만료 후 턴 상태 전달 지연

최신 후속: **2026-10-28 서버 AI 연출 여유 시간을 클라이언트가 잘라 조기에 0으로 표시하는 별도 문제를 재현·수정했다.** 아래10-25는 서버 전송 대기 경로, 마지막10-28 절은 클라이언트 카운트다운 경로다.

2026-10-25 소스 수정. 사용자 증상은 제한시간 종료 후 ‘내 턴 진행 중/처리 중...’ 안내가 1초에서 10초 이상 남는 경우다. 사용자는 사람 PvP/AI 중 어느 쪽인지 확실하지 않다고 답했다.

## 확인한 원인과 수정

- 기존 `ResolveTurnTimeoutAsync`는 공유 전투 판정으로 이미 다음 턴을 만든 뒤에도 감사 로그를 기다리고, 이벤트 전송·DB 스냅샷·결과 처리를 기다린 다음 StateView를 보냈다. 파일 쓰기 잠금이나 DB 지연이 다음 턴 통지를 막을 수 있었다.
- 기존 broadcast는 두 접속자에게 순서대로 전송했다. 소켓 전송은 5초 제한(전송 잠금 대기 포함)이 있으므로 한쪽의 느린 이벤트/상태 전송이 다른 정상 접속자의 상태를 늦출 수 있었다.
- 계속 진행되는 전투의 자동 턴 종료는 **다음 타이머 예약 → 접속자별 이벤트·전용 StateView 전송 → 감사 로그·스냅샷·결과 처리 → 필요한 AI 진행**으로 바꿨다. 각 기기 안에서는 이벤트→상태 순서를 지키되, 서로 다른 기기의 전송은 병렬 처리한다. StateView는 기존 소켓별 send gate 안에서 생성해 비공개 손패/트랩 필터링과 전투 기록 커서 순서를 보존한다.
- 기록은 생략하거나 fire-and-forget으로 바꾸지 않고 계속 await한다. 턴 만료 효과로 전투 자체가 끝난 경우에는 기존처럼 최종 StateView보다 **결과 저장을 먼저** 완료한다. 명령 검증, 중복 만료 방지, 기존 73초 deadline/턴 배너/멀리건 시간, 카드 효과, DTO와 클라이언트는 바꾸지 않았다.

실제 해당 전투에서 파일·DB·네트워크·연출 지연이 각각 몇 초였는지는 운영 로그 없이 확정할 수 없다. 이번 수정은 재현한 두 대기 경로를 제거한 것이며 실기기/운영 통신 지연의 상한을 보장하는 성능 측정은 아니다.

## 반영과 남은 확인

서버 재배포·재시작 후 운영에 반영된다. 이 수정만을 위해 클라이언트 빌드나 DB 마이그레이션은 필요 없다. 이번 작업에서 운영 서버 접속/배포·DB 작업·사용자 앱 빌드/설치·Unity Editor 조작은 하지 않았다. 재배포 후 기존 앱으로 사람 PvP 양쪽 좌석과 AI 전투에서 무행동 시간 만료를 확인하고, 턴 종료 효과가 있는 경우에도 정상 연출과 실제 차례를 함께 확인한다.

수정 전 재현 검사에서 실패를 처리하지 않은 .NET 예외로 종료해 Windows `dotnet.exe` 오류창이 떴다. 해당 격리 검사 프로세스만 실행 경로로 확인해 종료했다. 이후 검사는 실패 시 메시지와 종료 코드1을 반환하도록 바꿔 같은 원인의 오류창을 방지했다. 게임/운영 서버의 크래시가 아니며 재현 검사는 실제 DB나 계정에 접근하지 않았다.


## 2026-10-28 후속 — AI 연출 여유 시간을 잘라낸 클라이언트 타이머

사용자는 기존10-25 수정 후 Lightsail 서버 재배포까지 했다고 확인했다. PvP 모드의 서버 AI와 전투 중 자기10·12턴에서 무행동70초 후 `내 턴 처리 중...`이 약3~7초 남는다고 보고했다. 해당 실전의 패킷/운영 로그는 수집하지 않았으며, 아래는 현재 코드에서 같은 조기0 현상을 재현한 근거다.

### 원인

- 서버 `BattleSession.TryDelayCurrentPlayerTurnTimerForServerAiPresentation`과 `Program.BroadcastServerAiTurnIfNeededAsync`는 서버 AI의 공격·마법·카드 공개 등 클라이언트 연출이 진행되는 동안 다음 플레이어 턴 시간을 잃지 않도록 실제 deadline에 연출 여유 시간을 더한다.
- DTO의 `TurnTimerDurationSeconds`는 기존 명목 길이(일반 턴73초)이고 `TurnTimerDeadlineUnixTimeMilliseconds`는 연출 여유를 포함한 실제 만료 시각이다. 둘은 항상 같은 길이가 아니다.
- 클라이언트 `CalculateTurnTimerRemainingMilliseconds`가 남은 시간을 명목 길이로 제한했다. 예를 들어 명목73초+AI 연출7초의 실제 남은80초를73초로 줄여 `ShowOnlineTurnTimer`에 넘겼다. UI 코루틴은 그73초만 세므로 실제 서버 종료보다7초 먼저0이 되고 그 사이 `처리 중...`이 남는다. 같은 경로가3초/30초 여유에도 재현된다. 이전 서버 전송 개선만으로는 클라이언트의 이 잘라내기가 바뀌지 않는다.

| 실제 서버 기준 남은 시간 | 수정 전 UI 시작값 | 수정 후 UI 시작값 |
|---|---|---|
| 기본73 + 연출3 =76초 | 73초 | 76초 |
| 기본73 + 연출7 =80초 | 73초 | 80초 |
| 기본73 + 연출30 =103초 | 73초 | 103초 |

표는 패킷 수신 시점의 내부 카운트다운 값이다. AI 연출이 먼저 재생되는 동안 시간이 줄어들며, 서버의 기존 턴 길이·연출 시간 보정 정책이나 플레이 시간 규칙을 새로 늘린 것이 아니다. 기존 마지막20초 표시 정책과 서버 권위 판정도 유지한다.

### 수정·검증

- 실제 서버 deadline에서 보정된 현재 서버 시간을 빼서 남은 시간을 계산하고, 명목 길이로 자르는 코드를 제거했다. 기기 시계가 뒤로 크게 바뀌는 경우의 보호는 유지하되 상한을 명목 길이가 아닌 해당 서버 스냅샷이 알린 남은 시간으로 삼는다.
- 새 `OnlineTurnDeadlineTests`가 실제 private 계산/서버 시계 보정 함수를 호출한다. 일반 턴/멀리건, 연출3·7·30초, 새 상태/재접속 시점, 스냅샷 이후 시간 경과, 서버와 기기의 시계차·뒤로 이동, duration 필드 없는 호환 상태, 만료/없는 deadline을 확인한다. 실제70초를 기다리거나 시스템 시계/운영 서버를 바꾸지 않았다.
- 수정 전13건 중 **9건 실패**, 수정 후 새13건과 기존 OnlineBattleConnectionTester10/AiActionPacing23 = 실제 분리 Unity6000.3.12f1 **46/46 통과**, 실패/스킵0. 현재 소스/테스트와 검증 사본 SHA256 일치. 검증 사본에서만 기존 LevelPlay SDK 전용 assembly 제외 상태를 유지했으며 활성 프로젝트 광고 SDK는 변경하지 않았다.
- 증거: 세션 `AiTurnTimerPadding_20261028`의 `before-tests.xml`, `before.log`, `after-tests.xml`, `after.log`, `verification.json`, 원본 소스 스냅샷. 타이머 의미를 바꾸지 않고 UI가 서버 만료 시각을 따르도록 한 클라이언트 변경이다.

### 반영·확인 범위

**사용자 클라이언트 재빌드·휴대폰 재설치가 필요하다.** Unity Editor에서는 재컴파일 후 확인한다. 이번 클라이언트 수정 때문에 서버 재배포나 DB 마이그레이션을 할 필요는 없다. 앱 빌드/설치·운영 배포·DB 접속은 실행하지 않았다.

새 앱에서 서버 AI가 카드 사용/공격을 여러 번 한 다음, 다음 내 턴에 무행동으로 제한시간 만료를 확인한다. 카운트다운이0이 되는 시점과 실제 차례 전환이 맞는지 확인한다. 이번 재현은 연출 보정이 잘리는 경로를 확인한 것이며 방금 실전의3~7초 전체 원인, 네트워크/서버 부하/전송 지연까지 제거됐다는 보증은 아니다. 남는 지연이 있다면 실제 이벤트 수신·deadline·턴 전환 타임스탬프로 별도 구간을 좁힌다.
