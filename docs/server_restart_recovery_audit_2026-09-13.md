# After333 서버 재시작 전투 복구 점검 — 2026-09-13

> 이 문서는 작성 당시의 보고서·검증 이력이다. 과거 카드/DB버전·미완료 항목·가동 상태를 오늘의 상태로 적용하지 않는다. 2026-10-20 현재 정리는 [프로젝트 상태](current_project_status.md), 운영은 [Lightsail 안내](lightsail_operations.md)를 따른다. 당시 측정값·성공/실패 기록은 보존한다.

## 후속 결정과 구현

사용자가 서버 중단 시 미완료 전투를 승패 없이 취소하도록 확정했다. 아래 내용은 변경 전 소스 점검 기록이다. 이후 스냅샷으로 전투를 이어가는 런타임 경로를 제거하고 취소 처리를 구현·격리 검증했다. [현재 처리 규칙과 검증](./server_interruption_cancellation_2026-09-13.md)을 우선 참조한다. 아래의 복구 대기 시간·턴 시계 정책 제안은 더 이상 구현 예정 사항이 아니다.

## 범위와 결론

현재 소스를 읽어 서버 프로세스가 전투 도중 종료된 경우의 복구 경로를 점검했다. 운영 서버 종료·재시작, 운영 DB 변경, 앱 빌드 및 새 장애 주입 테스트는 실행하지 않았다. 아래 결함은 코드 경로 분석 결과이며 실제 발생 빈도나 운영 재현 완료를 뜻하지 않는다.

PvP의 기본 스냅샷 저장·복원은 이미 구현되어 있다. 따라서 복구 기능 전체가 미구현이라는 표현은 부정확하다. 다만 저장 성공의 보장, 재시작 후 참가자 대기·만료 처리, 턴 시계와 PvE 복구가 충분히 연결되어 있지 않다. 기존 결과 저널 보호나 일반 연결 끊김 테스트 통과를 진행 중 전투의 서버 재시작 검증 완료로 확대해서는 안 된다.

## 구현된 부분

- 운영 실행 스크립트는 기본적으로 시작 시 PvP 복구를 활성화한다. Program.cs는 진행 중 DB 경기와 참가자를 재접속 대기로 옮기고 이전 프로세스의 연결을 닫힌 상태로 표시한다. 저수준 직접 실행에서는 설정에 따라 비활성일 수 있다.
- PvP 재접속 시 메모리에 경기가 없으면 최신 DB 스냅샷으로 BattleSession을 복원한다. 손패·덱 순서·자원·필드·지속 효과·멀리건 사용 여부·턴 상태·참가자 런/덱/강화 정보·결과 ID·전투 로그를 담는 구조가 있다. 이 목록은 모든 카드 상호작용의 복원 검증 완료를 뜻하지 않는다.
- 이미 종료된 경기는 결과 저널을 디스크에 기록한 후 전송하는 보호, 재시작 후 재처리, 결과 ID에 따른 중복 반영 방지가 있다. 저널이 저장된 디스크가 유지되어야 한다. MYBOX DB 덤프에는 DB 밖의 미처리 결과 저널이 포함되지 않는다.
- 기존 ResultDeliveryChecks에는 스냅샷 직렬화 후 새 세션의 결과 귀속·결과 ID 복원과 결과 저널의 프로세스 재처리 검사가 있다. 실제 두 클라이언트의 진행 중 전투를 서버 강제 종료 전후로 이어가는 종합 검사를 대신하지 않는다.

## 발견한 문제와 우선순위

### 1. 저장 실패 후에도 성공한 행동으로 응답할 수 있음 — 우선 보강

Program.cs의 명령 처리 순서는 메모리 전투 변경 → 명령 기록 → 스냅샷 기록 → ACK다. 하지만 두 기록 도우미는 저장 예외를 로그만 남기고 삼킨다. 따라서 DB 장애 중 일반 행동의 저장이 실패해도 ACK를 보낼 수 있다. 이후 프로세스가 종료되면 최신 저장 상태로 돌아가 방금 성공한 소환·공격 등이 사라질 수 있다.

명령 기록과 스냅샷은 별도 트랜잭션이다. 현재 복구는 최신 스냅샷만 사용하고 명령 기록을 재실행하지 않는다. 명령 기록이 남았다는 사실만으로 누락된 상태가 자동 복구되지는 않는다. 전투 종료 결과는 별도 저널 보호가 있으므로 동일하게 전부 유실된다고 단정하지 않는다.

근거: Program.cs 1873–1916, 2618–2646, 2740–2785; BattlePersistence/PvpBattlePersistenceService.cs의 RecordCommandAsync/RecordSnapshotAsync/LoadLatestSnapshotAsync.

개선 방향: 경기별로 행동 적용·영구 기록·성공 응답의 순서를 보장하고, 저장 실패 시 다음 행동을 계속 받지 않도록 설계한다. 예외를 다시 던지기만 하면 이미 변경된 메모리가 남으므로 그것만으로 해결되지 않는다. 상태 복원 또는 안전한 정지·재처리까지 함께 정해야 한다.

### 2. 한쪽 또는 양쪽이 돌아오지 않을 때 재시작 후 만료 처리가 빠짐 — 우선 보강

시작 시 DB 상태만 바꾸고 모든 진행 경기의 메모리 세션·만료 작업을 재생성하지 않는다. 첫 사용자가 돌아오면 그 사용자 좌석의 재접속 예약만 복원하며, 상대 좌석의 예약과 만료 작업은 함께 복원하지 않는다. 예약된 좌석은 해당 사용자가 들어오면서 제거된다.

일반 연결 종료에서는 ResolveDisconnectForfeitAfterGraceAsync를 예약하지만 이 호출은 종료 처리 경로에만 있다. 서버 재시작은 기존 프로세스의 대기 작업을 잃는다. 아무도 돌아오지 않으면 전투를 불러오지도 않는다. DB 재접속 조회는 기한이 지난 행을 제외하며, 매칭 예약 만료 정리는 시작 전 waiting 경기를 대상으로 하므로 이 누락을 대신 처리하지 않는다.

그 결과 한쪽 미복귀를 정상 재접속 기권으로 마무리하지 못하거나, 양쪽 미복귀 경기가 DB에 미종료 상태로 남을 경로가 있다. 구체적인 화면·최종 성적 영향은 새 종합 테스트로 확인해야 한다.

근거: Program.cs 90–105, 1595–1631, 1960–1973, 2374–2426, 2700–2729; BattleSession.cs TryRestorePendingReconnectReservation/TryAssignPendingReconnectSeat; PvpMatchmakingService.cs 17–151; PvpMatchReservations.cs ExpireReservationsAsync/CancelEmptyWaitingMatchesAsync.

개선 방향: 복구 대상 경기 전체와 양쪽 참가자 상태를 함께 다루고, 재접속자가 없어도 만료 후 정리할 수 있게 한다. 서버 장애로 인한 미복귀를 개인 통신 끊김과 같은 패배로 처리할지는 사용자 규칙 확정이 필요하다.

### 3. 서버가 꺼진 시간도 기존 턴 기한에 포함됨 — 처리 규칙 필요

복원은 원래의 절대 UTC 턴 종료 시각을 그대로 사용한다. 이미 기한이 지났으면 접속 후 예약되는 턴 타이머가 즉시 만료할 수 있다. 타이머 처리에는 양쪽 접속 완료나 서버 장애 시간 제외 조건이 없다. 따라서 복귀 직후 멀리건 자동 완료 또는 턴 종료가 가능하다.

시작 시 일반 활성 참가자에게는 현재 시각 기준 재접속 유예(현재 60초)를 부여하지만, 기존의 아직 유효한 재접속 기한은 유지하고 이미 만료된 disconnected 참가자는 갱신하지 않는다. 서버 중단 시간과 기존 개인 단절이 겹치면 참가자별 복귀 가능 시간이 달라질 수 있다.

근거: BattleSession.cs RestoreFromPersistenceSnapshot의 TurnTimerDeadlineUtc 복원(614행), TryGetTurnTimer/TryCreateTurnTimeoutEnvelope(680–830행 부근); Program.cs 1791 부근 및 ScheduleTurnTimeoutIfNeeded; PvpMatchmakingService.cs 시작 복구 SQL.

결정할 규칙: 서버 장애 시간을 턴 제한에서 제외할지, 재개할 때 남은 시간을 돌려줄지/새 시간을 줄지, 한쪽만 돌아온 상태에서 전투를 진행할지. 현재 동작을 사용자 확정 규칙으로 간주하지 않는다.

### 4. PvE는 프로세스 재시작 후 이어하기 경로가 없음

PvE 재접속은 BattleSessionManager의 메모리 세션 조회를 사용한다. 프로세스가 바뀌면 이전 전투가 없어 battle_reconnect_expired를 응답한다. PvE는 PvP 경기·접속 등록에서도 제외되며, 스냅샷 서비스는 대응 경기 행이 없으면 저장하지 않고 반환한다. snapshot 클래스가 PvE 상태를 표현할 수 있다는 사실과 실제 운영 PvE 저장·복원 경로가 있다는 것은 다르다.

근거: Program.cs 1576–1592, RecordPvpMatchmakingJoinAsync/RecordPvpBattleStartedIfNeededAsync; BattleSessionManager.cs FindReconnectableServerAiBattle; PvpBattlePersistenceService.cs 35–42.

개선 방향: PvE도 복구 대상으로 저장하거나, 서버 장애로 중단된 경기의 종료 정책을 정해 처리한다. 종료 결과가 확정되기 전의 경기를 임의로 패배 처리하거나 티켓을 지급하지 않는다.

### 5. 최신 스냅샷이 실제 최신 전투 상태라는 보장이 약함

전투 잠금 안에서 스냅샷을 만든 뒤 DB 저장은 잠금 밖에서 수행한다. DB의 경기 행 잠금은 snapshot_version 할당을 직렬화하지만, 이는 DB 저장 순서이며 전투 상태 생성 순서가 아니다. 접속 처리·타이머·명령 처리가 겹쳐 이전에 캡처한 상태가 더 늦게 저장되면 더 큰 버전을 받을 가능성이 있다. 복구는 가장 큰 버전 하나를 선택하며 상태 순번에 의한 역행 차단을 하지 않는다.

또한 최신 스냅샷이 없거나 읽기/복원에 실패하면 복구 불가 응답 또는 재접속 불가가 되고, 명령 기록 재생·검증된 대체 상태 복구·장애 종료로 이어지는 정책은 없다. 이전 버전으로 무조건 되돌리는 것도 성공한 행동을 잃을 수 있어 안전한 해결로 볼 수 없다.

근거: BattleSession.cs CreatePersistenceSnapshot; Program.cs RecordPvpBattleSnapshotAsync/RestorePvpBattleSessionFromLatestSnapshotAsync; PvpBattlePersistenceService.cs RecordSnapshotAsync/LoadLatestSnapshotAsync.

개선 방향: 1번과 함께 경기별 상태 생성부터 저장까지 순서를 보장하고, 상태 버전·중복 처리·복구 실패 정책을 명시한다. 저장 순서 역전은 이번에는 소스상 경합 가능성을 확인했으며 지연 주입 재현은 아직 하지 않았다.

## 권장 진행 순서

1. 저장 실패에도 성공 응답하는 경로와 스냅샷 순서 보장을 함께 보강한다.
2. 서버 장애 시 복구 대기 시간·턴 시계·미복귀/복구 불가 경기의 성적 처리 규칙을 사용자에게 확정받는다.
3. 확정 규칙으로 PvP 양쪽 참가자 및 PvE 복구·정리를 연결한다.
4. 별도 합성 DB와 테스트 계정으로 실제 서버 프로세스를 종료·재시작하는 검사를 수행한다. 운영 서버나 실제 계정으로 처음 재현하지 않는다.

종합 검사에는 양쪽 복귀, 한쪽만 복귀, 양쪽 미복귀, 기존 개인 단절 중 서버 종료, 멀리건/일반 턴/종료 결과 저장 중 종료, DB 저장 실패, 저장 순서 역전, 복구 불가 스냅샷, PvE, 반복 재시작을 포함한다. 손패·자원·필드·턴·승패의 유지, 중복 결과 없음, 남은 경기/예약의 정리를 확인한다.

현재는 분석 및 문서화까지만 완료했다. 게임 코드·DB 스키마·서버 배포 및 실행 상태는 변경하지 않았다.
